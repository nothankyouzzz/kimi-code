# Resolve Patched-Upgrade Conflicts

This runbook guides you through diagnosing, rebasing, and verifying patch branches when the Kimi patched upgrade pipeline encounters conflicts.

## Overview & Pipeline Mechanics

The local Kimi binary is built from an upstream release plus local patch branches.
- **Pipeline script**: `~/.kimi-code/upgrade-with-patches.sh` (source maintained at `scripts/patched-upgrade/` on branch `local/upgrade-hook`).
- **Patch registry**: `~/.kimi-code/local-patches.json`. Stores `patches[]` (`branch`, `pr`, `status`) and local `state`. **Do not edit this file by hand**; the pipeline manages it.
- **Remote-first sourcing**: By default, the upgrade script fetches from `origin`, builds using `origin/<branch>`, and fast-forwards local branches that are strictly behind. Unpushed local rebases are invisible to the upgrade script unless overridden.
- **Local development flag**: Set `KIMI_PATCH_LOCAL=1` to build from local branch tips instead of `origin` and skip fetching `origin`.
- **Merge simulation gate**: Before building, the script runs `git merge-tree --write-tree` for each active patch against `upstream/main`. This check simulates merges without touching branches. If any patch conflicts, the pipeline halts immediately, leaving the existing binary intact.
- **Merged PRs**: When an upstream PR is marked MERGED, the pipeline sets `status: "merged"` in the registry and skips it. Do not rebase merged patches.

### Key Environment Variables

| Variable | Description |
|---|---|
| `KIMI_PATCH_REPO` | Path to the local repo checkout (defaults to `.state.repoPath` recorded at installation). |
| `KIMI_PATCH_STATE` | Path override for the registry/state JSON file. |
| `KIMI_PATCH_LOCAL=1` | Source patches from local git branches instead of `origin`; bypasses `origin` fetch. |
| `DRY_RUN=1` | Runs preflight checks and merge simulations without building or installing. |
| `FORCE=1` | Forces a rebuild even if the release version and patch hashes are unchanged. |
| `SKIP_TYPECHECK=1` | Bypasses the TypeScript compile check gate. |
| `KIMI_UPGRADE_STRICT_SELFCHECK=1` | Makes script and registry drift fatal instead of emitting a warning. |

## When This Skill Applies

Trigger this workflow when the upgrade script exits with any of the following errors:

1. **Merge gate failure**:
   ```
   ERROR: patch <branch> has merge conflicts vs upstream/main: <paths>
   ```
   One or more active patch branches cannot merge cleanly into `upstream/main`.
2. **Cherry-pick failure**:
   ```
   conflict applying <branch> onto <tag>
   ```
   Git encountered conflicts while applying the patch during the build stage.
3. **Self-check drift warnings/errors**:
   - `ERROR: self-check: ... differs from the versioned source ...`: The live hook script or skill drifted from `local/upgrade-hook`. Reinstall using:
     ```bash
     FORCE=1 bash <repo>/scripts/patched-upgrade/install.sh
     ```
     (Warns by default; fatal if `KIMI_UPGRADE_STRICT_SELFCHECK=1` is set. Skill differences never block.)
   - `self-check: patch registry drift ...`: Active patches in `local-patches.json` differ from the repo's bundled list. (Warns by default; fatal under strict mode. Legitimate runtime updates like `merged` marks and `state` fields are ignored.)
4. **Pre-upgrade check**: Run this workflow proactively before upgrading to identify and fix conflicts in advance.

## Workflow Step-by-Step

### Step 1: Pre-Scan & Enumerate Conflicted Branches

Before checking conflicts, synchronize your local tracking branches with `origin` so your local environment matches what the pipeline will build:

```bash
cd "$REPO"
git fetch origin --prune

# Fast-forward local branches that are strictly behind origin
jq -r '.patches[] | select(.status=="active") | .branch' ~/.kimi-code/local-patches.json \
  | while read -r b; do
      git rev-parse --verify --quiet "refs/remotes/origin/$b" >/dev/null || continue
      git merge-base --is-ancestor "refs/heads/$b" "refs/remotes/origin/$b" 2>/dev/null || continue
      git branch -f "$b" "origin/$b" 2>/dev/null || true
    done
```

Next, test each active branch against `upstream/main`:

```bash
cd "$REPO" && git fetch upstream main

jq -r '.patches[] | select(.status=="active") | .branch' ~/.kimi-code/local-patches.json \
  | while read -r b; do
      ref=$(git show-ref --verify --quiet "refs/remotes/origin/$b" && echo "origin/$b" || echo "$b")
      printf '%s: ' "$b"
      git merge-tree --write-tree --name-only upstream/main "$ref" >/tmp/mt.out 2>&1 \
        && echo clean \
        || { echo CONFLICT; sed -n '2,/^[[:space:]]*$/p' /tmp/mt.out | sed '/^[[:space:]]*$/d'; }
    done
```

**Diagnose results**:
- `clean`: Branch merges without conflicts. No action needed.
- Only `docs/state-manifest.d.ts` listed: Harmless compiler-generated type drift. The pipeline auto-resolves this; ignore it.
- Already merged upstream (`git merge-base --is-ancestor <ref> upstream/main` returns 0): Upstream has incorporated the branch; skip rebasing.
- Any other conflicting files: The branch needs rebasing. Proceed to Step 2.

---

### Step 2: Rebase and Resolve Conflicts

For each branch that failed the scan:

```bash
git checkout <branch>
GIT_EDITOR=true git rebase upstream/main
```
*(Setting `GIT_EDITOR=true` prevents git from suspending on commit message prompts.)*

#### Resolution Mindset
Preserve the **intended functional behavior** of the patch within the new upstream structure. When upstream refactors surrounding code, adapt the patch to fit upstream's updated architecture rather than forcing obsolete file structures to remain.

Search upstream first to locate where relevant code or symbols moved:
```bash
git grep <symbol> upstream/main -- <dir>
```

#### Conflict Triage Table

| Category | Typical Scenarios | Action Required |
|---|---|---|
| **Quiet-fix** (Deterministic, no judgment call) | - Simple import statement conflicts (retain both sides)<br>- Documentation or ordered lists (merge entries, renumber)<br>- Upstream partially adopted the fix (apply only the remaining delta) | Resolve conflicts, run tests, and continue. No extra report needed beyond the standard summary. |
| **Report-but-continue** (Architectural choice made) | - Module moved or renamed upstream (patch re-homed to a new location)<br>- Modifications to user-visible or model-visible strings (error messages, prompts, protocol payloads)<br>- Patch logic expanded into new files that the original commit did not touch | Resolve conflicts, verify gates, and document your decision and rationale in the final summary. |
| **STOP and ask** (User decision required) | - Multiple valid resolution strategies exist with different trade-offs<br>- Upstream appears to have implemented identical functionality (decide whether to drop or adapt patch)<br>- Security-sensitive code: preflight checks, command spawning, PATH resolution before workspace trust, authentication, permission gates (e.g. `apps/kimi-code/src/cli/update/preflight.ts`) | **Do not guess.** Halt resolution, document the options, and ask the user for direction. |

*Rule of thumb*: If unsure between Quiet-fix and Report-but-continue, always report your decision.

#### Finalize the Rebase
1. Check files that auto-merged: Upstream refactoring may mean parts of the patch need to be mirrored in newly split files (e.g., `projection.ts` vs `mediaProjection.ts`).
2. Stage resolved files:
   ```bash
   git add <resolved-files>
   GIT_EDITOR=true git rebase --continue
   ```
3. Maintain clean commit history. Squash any test fixes or follow-up adjustments directly into the relevant patch commit:
   ```bash
   git commit --fixup <commit-sha>
   GIT_SEQUENCE_EDITOR=: GIT_EDITOR=true git rebase -i --autosquash upstream/main
   ```

### Step 3: Verification Gates

Every rebased branch must satisfy all three gates before the pipeline will accept it:

1. **Merge simulation check**:
   ```bash
   git merge-tree --write-tree --name-only upstream/main <branch>
   ```
   Must return 0 (or only conflict on `docs/state-manifest.d.ts`).

2. **TypeScript compilation**:
   Ensure dependencies are up to date and typecheck all packages modified by the branch:
   ```bash
   pnpm install
   git diff --name-only upstream/main HEAD \
     | sed -n 's@^\(packages/[^/]*\|apps/[^/]*\)/.*@\1@p' | sort -u \
     | while read -r p; do (cd "$p" && pnpm exec tsc -p tsconfig.json --noEmit) || exit 1; done
   ```

3. **Package tests**:
   If changes were made to code or behavior, run the relevant package test suite:
   ```bash
   pnpm --filter <pkg> test <test-file>
   ```

---

### Step 4: Validate Upgrade & Finalize

#### 1. Test Locally (Dry Run)
Before pushing to remote, test the entire pipeline using your local branches:
```bash
KIMI_PATCH_LOCAL=1 DRY_RUN=1 ~/.kimi-code/upgrade-with-patches.sh
```
This validates all local branches against upstream release gates without modifying the installed binary.

#### 2. Push Rebased Branches
Because the production pipeline pulls from `origin`, push your updated branches:
- **Confirm with the user before pushing.**
- Push to origin:
  ```bash
  git push origin <branch> --force-with-lease
  ```

#### 3. Run the Upgrade Pipeline
Run the normal upgrade command:
```bash
~/.kimi-code/upgrade-with-patches.sh
```

#### 4. Post-Upgrade Verification Checklist
Confirm successful installation:
- [ ] Console logs report: `done: kimi <version> + N patch(es) installed`.
- [ ] Log shows patches resolved to `origin/<branch>` (or synced local branches).
- [ ] Binary version matches expected release: `~/.kimi-code/bin/kimi --version`.
- [ ] Registry state updated in `~/.kimi-code/local-patches.json` (`baseRelease`, `builtHash`, `builtAt`).
- [ ] Previous binary backup created at `~/.kimi-code/bin/kimi.prev.bak`.
- [ ] Git repository is restored to its original working branch with a clean tree.

*(Note: Rebasing generates new commit hashes, altering the patch fingerprint. A full rebuild is normal and expected even when upgrading against the same release version.)*

## Red Lines & Hard Rules

- **Never push to `origin` without user consent.** Rebases rewrite history; pushing requires explicit confirmation.
- **Never assume local rebases affect the normal upgrade.** The pipeline reads `origin/<branch>` unless `KIMI_PATCH_LOCAL=1` is specified.
- **Never hand-edit `~/.kimi-code/local-patches.json`.** The upgrade pipeline manages patch statuses and machine state.
- **Never proceed without a green `git merge-tree`.** An unverified branch will break the pipeline gate.
- **Never guess on security-sensitive code.** Spawning processes, authentication, and trust preflights require user sign-off.
- **Never drop test coverage.** Rebased patches must pass their test suites to prevent regression or behavioral drift.
